**Course:** AI-Enabled Software Development / Software Engineering

**Duration:** 3 Hours
**Mode:** Individual or Pair Work

---

# 1. Lab Overview

AI coding assistants can generate code very quickly. However, generating code quickly does not necessarily mean that we are building the **right software**.

A common workflow is:

> Idea → Prompt AI → Generate Code → Fix Problems → Prompt Again → More Code

In this lab, you will use **Spec-Driven Development (SDD)** instead:

> Idea → Specification → Clarification → Technical Plan → Tasks → Analysis → Implementation

Instead of treating documentation as something written after development, SDD treats the **specification as the source of truth for implementation**.

You will use **GitHub Spec Kit** with an AI coding agent to take one application feature through the complete SDD lifecycle.

---

By the end of this lab, you should be able to:

1. Explain the purpose of Spec-Driven Development.
2. Install and initialize GitHub Spec Kit.
3. Identify the main files and directories generated by Spec Kit.
4. Define project-wide engineering principles using `/speckit.constitution`.
5. Translate a feature idea into a structured specification using `/speckit.specify`.
6. Identify and resolve ambiguous requirements using `/speckit.clarify`.
7. Transform requirements into a technical implementation plan using `/speckit.plan`.
8. Generate implementation work using `/speckit.tasks`.
9. Check consistency between specification, plan, and tasks using `/speckit.analyze`.
10. Implement a feature using `/speckit.implement`.
11. Evaluate whether the final implementation satisfies the original specification.

### Checkpoint

Before continuing, explain to your partner:

> What is the difference between `spec.md`, `plan.md`, and `tasks.md`?

Write your answer:

**spec.md**
Defines **WHAT** is being built and **WHY** from the user's perspective. It describes user stories, business outcomes, functional requirements, non-goals (boundaries), and checkable acceptance scenarios without specifying technical implementation details.

**plan.md**
Defines **HOW** the system will technically fulfill the specification. It translates user requirements into technical architecture, file changes, data schemas, API/output contracts, dependencies, and error handling strategies.

**tasks.md**
Converts the technical plan into actionable, sequential units of **WORK**. It breaks down implementation into discrete setup, coding, and testing tasks with explicit dependencies so an AI agent or engineer can execute them without context overload.

# Part 4 — Establish the Project Constitution

**Suggested time: 20 minutes**

Before specifying individual features, establish the engineering principles that should govern the project.

Launch your AI coding agent inside the project.

Run:

```text
/speckit.constitution
```

Do not simply ask it to create generic principles.

Provide meaningful engineering expectations.

Example:

```text
/speckit.constitution

Create project principles based on:

- readable and maintainable code
- separation of concerns
- simple architecture over unnecessary complexity
- automated testing for important business logic
- input validation and error handling
- secure management of secrets
- consistent user experience
- documentation for important architectural decisions
- no implementation should be considered complete unless its acceptance criteria can be verified
```

Open the generated constitution.

### Inspect

Identify at least three rules that could affect future implementation.

| Principle | How might this affect implementation? |
| --------- | ------------------------------------- |
| 1. Defensive Error Handling & User-Facing Safety | The CLI must catch all file system/OS errors or invalid arguments and return clear messages; it must never crash or output a raw Python traceback. |
| 2. Separation of Concerns & Clean Architecture | File formatting, serialization, and disk persistence cannot be dumped into `main.py`; they must live in an isolated module (`exporter.py`). |
| 3. Automated Verification & Quality Gates | No feature is complete without automated unit tests verifying valid outputs (Markdown/JSON) and guarding against edge cases (empty history, invalid formats). |

### Think

Why should the constitution be created **before** the feature plan?

The constitution defines foundational, non-negotiable architectural boundaries, coding standards, and operational guidelines for the entire repository. If established beforehand, every subsequent feature specification, technical plan, and task list must conform to these universal rules, preventing architectural drift, inconsistent error handling, and technical debt before code is written.

# Part 6 — Specify: Define WHAT and WHY

**Suggested time: 25 minutes**

Now create the specification.

Run:

```text
/speckit.specify
```

Describe the feature from the **user's perspective**.

Focus on:

* Who needs the feature?
* What should they be able to do?
* Why do they need it?
* What behavior should they observe?
* What counts as success?

Avoid telling the AI exactly how to implement it.

### Example

Instead of:

```text
/speckit.specify

Create a React search component using useState,
call GET /api/tasks?q=query and debounce it by 300ms.
```

write:

```text
/speckit.specify

Users need to search their tasks by title.

A user can enter part or all of a task title and see matching
tasks. Search should not be case-sensitive.

When there are no matching tasks, the application should clearly
show that no results were found.

Clearing the search should restore the complete task list.
```

The first example describes **HOW**.

The second describes **WHAT and WHY**.

Open the generated specification.

### Specification Review

Answer:

**1. Who is the user?**
A software engineering student or developer using the Configurable Text Assistant CLI who wants to save, inspect, and share session transcripts and token metrics.

**2. What problem are they trying to solve?**
Interactive sessions are ephemeral in terminal memory; once the program terminates or resets, dialogue turns, prompts, and token usage counts are completely lost.

**3. List two acceptance criteria.**

1. Invoking `/export` in an active session generates a timestamped Markdown transcript (`session_<persona>_<timestamp>.md`) containing the metadata table, system prompt, and chronological user/assistant turns.

2. Invoking `/export` in an empty session (zero user interactions) creates no files and displays the user message: `"No messages to export yet."`.

**4. Find one requirement that could still be interpreted differently by two developers.**
How target subdirectories should be handled (e.g. `/export archives/session1.md`): one developer might require the folder `archives/` to already exist and throw an error if missing, while another might automatically create the missing parent directories recursively.

That ambiguity is what we will address next.

# Part 7 — Clarify: Remove Ambiguity

**Suggested time: 20 minutes**

A specification can look detailed and still contain hidden assumptions.

Run:

```text
/speckit.clarify
```

Let the agent identify underspecified areas.

Do not answer automatically.

For every question, consider:

> Would two different developers make different implementation decisions because this requirement is unclear?

Example clarification questions might concern:

* What happens when no results exist?
* Is search case-sensitive?
* Who has permission?
* What happens when the network fails?
* How much data should be shown?
* Should deleted records appear?
* What does "fast" actually mean?

Respond to the clarification questions.

Then inspect the updated specification.

### Record Three Clarifications

| Before Clarification | Decision |
| -------------------- | -------- |
| 1. What happens if a user exports an empty conversation with 0 user turns? | Guard against empty exports: display `"No messages to export yet."` and do not create any file. |
| 2. What file formats and extensions should be allowed? | Strictly allow `.md` (Markdown) and `.json` (JSON); reject any other extension with `"Unsupported format. Please use .md or .json."`. |
| 3. What should happen if target destination subdirectories do not exist? | Automatically create missing parent directories (`mkdir(parents=True, exist_ok=True)`) to provide seamless developer experience. |

### Reflection

Which clarification would have caused the biggest implementation problem if it had not been resolved?

Strictly limiting supported file formats to `.md` and `.json` and specifying the exact rejection behavior for others.

Why?

Without explicitly constraining file formats and extensions, an AI coding agent or teammate might attempt to add generic converters for `.pdf`, `.docx`, or `.csv`, pulling in large external libraries (e.g., ReportLab, python-docx), violating project constraints, and breaking when those packages are missing.


# Final Reflection

Answer each question briefly.

## 1. Before this lab, how would you normally implement this feature?

Before this lab, I would typically jump straight into the code editor (`main.py`), write an ad-hoc `/export` condition, quickly append file write calls using default Python `open()`, and manually test it once or twice in the console. Edge cases, format schemas, and error boundaries would only be handled reactively when something crashed.

## 2. What changed when you were forced to specify the feature before coding?

Specifying the feature first forced me to think from the end user's perspective rather than the code's perspective. It clarified exactly what data needed to be exported, forced me to define what an "empty" session actually means, required locking down format boundaries (`.md` and `.json` only), and led directly to writing clean, decoupled, and testable code on the first attempt without refactoring loops.

## 3. Which command had the greatest effect on implementation quality?

```text
/speckit.constitution
/speckit.specify
/speckit.clarify
/speckit.plan
/speckit.tasks
/speckit.analyze
/speckit.implement
```

**`/speckit.clarify`**

Why?
Because the initial idea and specification always contain implicit assumptions that developers take for granted. `/speckit.clarify` systematically probed underspecified edge cases (e.g., what happens when no user messages exist, whether to overwrite or append, which file extensions to allow, and how to handle missing parent directories). Resolving these before coding eliminated scope ambiguity completely.

## 4. What ambiguity did `/speckit.clarify` expose that you might otherwise have ignored?

The definition of an "empty" conversation. In our assistant, every session starts with a system prompt pre-populated in `self.messages`. A naive developer or agent checking `if not messages:` would never detect an empty session and would export useless files containing only system instructions. Clarification ensured we explicitly check for non-system messages (`user` or `assistant`).

## 5. Did `/speckit.analyze` identify anything that humans or the AI had missed?

Yes. `/speckit.analyze` identified a traceability gap: `spec.md` required exporting token consumption metrics, but `Session.messages` in `main.py` only contained role/content dictionaries. The initial plan had not specified how `exporter.py` would access the token statistics stored in `LLMService.total_usage`. We resolved this by defining an explicit `metadata` contract object passed into `export_session()`.

## 6. What is one disadvantage or cost of adopting SDD?

The upfront time and cognitive overhead. Writing a constitution, specification, technical plan, and task breakdown requires noticeable preparation before writing any executable code. For trivial one-off bug fixes or experimental prototypes, this ceremony can feel disproportionate.

## 7. For what kind of development work do you think SDD would be most useful?

SDD is most effective for collaborative team environments, AI-assisted/delegated coding pipelines, public APIs, and mission-critical features with strict data contracts. In these contexts, ambiguity leads to costly misunderstandings, scope creep, and broken interfaces, making SDD's upfront discipline a major net time-saver.

# Key Takeaway

The purpose of this lab is **not to learn seven slash commands**.

The commands represent different software-engineering decisions:

```text
Constitution → What principles must we follow?

Specify      → What are we building and why?

Clarify      → What don't we understand yet?

Plan         → How should we build it?

Tasks        → What exactly needs to be done?

Analyze      → Do our requirements, design and tasks agree?

Implement    → Now, write the code.

Validate     → Did we actually build what we specified?
```

The central idea of Spec-Driven Development is:

> **The specification drives the implementation; the implementation does not define the specification.**
